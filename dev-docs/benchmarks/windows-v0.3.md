# ziptensors native Windows decode timing (format 0.3, risk R4)

Measured 2026-11-07. The question: does decoding on Windows run in the range the CPU predicts, or is
there a Windows-specific slowdown (positional reads through `seek_read`, the rayon pool)?
GB is 10^9 bytes. All times are in seconds except random-read latencies, which are in milliseconds.

## Setup

| | Windows | Linux (reference) |
|---|---|---|
| CPU | AMD Ryzen 5 4600H (Zen 2 laptop, 6 cores / 12 threads) | AMD Ryzen 5 9600X (Zen 5 desktop, 6 cores / 12 threads) |
| OS | Windows 11 (build 26200), power plan Balanced | Linux 7.0 |
| Storage of data and outputs | NVMe SSD (WD PC SN730), NTFS, files warm in the OS cache | tmpfs (RAM) |
| Build | native `x86_64-pc-windows-msvc`, `cargo build --release -p ziptensors-cli` | `x86_64-unknown-linux-gnu`, same command |
| Machine load | idle laptop (CPU load 7% when sampled) | shared box, load average 15 to 53 during the main run and 45 to 72 during the follow-up |

Both binaries were built from the same source snapshot with the workspace release profile (thin LTO, one
codegen unit). An antivirus with on-access scanning is active on the laptop; no binary vanished
during this run.

Data: two seeded synthetic safetensors files, generated by a small numpy script outside the tree and
copied byte-identically (sha256 checked) to the laptop. No real model was used. Weight matrices are
normal noise with a per-tensor scale drawn log-uniformly in [0.005, 0.1]. Every eighth tensor is a norm
vector, 1 + 0.05 noise, rounded to the dtype (BF16 by round-to-nearest-even):

- `bf16`: 72 tensors, mostly 4096 x 4096, 2.114 GB.
- `f32`: 36 tensors, mostly 2048 x 4096, 1.074 GB.

What each measurement does:

- `encode`: `ziptensors encode <src> <out> --mode M`, default threads. It includes the commit, which
  decodes the output once more and syncs it.
- `verify`: `ziptensors verify --threads T`, a full decode with the per-chunk XXH3 and the
  whole-member BLAKE3, with nothing written.
- `restore`: `ziptensors restore --threads T` to a new file. On Windows it writes to NVMe and syncs;
  on Linux it writes to tmpfs, so the two `restore` columns are not comparable.
- `read-all`: a scratch probe that calls `Member::read_at` in 64 MiB steps over the whole member, with
  no hash and no write. This is the closest measure of decode speed through the file.
- `read-all-mem`: the same, over the container held in memory through `Container::from_source`, so no
  OS I/O is involved.
- `random`: 300 reads of 1 MiB at 4 KiB-aligned seeded offsets (identical on both machines), timed
  per call. Packed reads go through `Member::read_at`; raw reads go through `FileSource::read_exact_at`
  on the source safetensors, which is the same `seek_read`/`pread` path.
- `memcpy`: a 1 GiB copy in 1 MiB or 64 MiB pieces, best of 5. It calibrates CPU and memory speed.

Threads are 1 and 0 (the default, one per logical CPU, 12 on both machines). Each decode case ran 3
times, back to back, with the files warm in the OS cache. Tables show the median of 3 (2 for random).
Encode ran once per mode.

## Conclusion

**Single-thread decode on Windows is within the expected range.** The Windows laptop decodes at 0.46 to
0.53 of the Linux desktop's speed per thread, whether the container is read through the file or held
in memory. That matches the hardware ratio measured by the 1 MiB memcpy (0.50) and the gap between a
Zen 2 laptop and a Zen 5 desktop. The decode itself shows no Windows-specific cost.

**Positional reads cost more on Windows, but not abnormally.** With one thread, reading through the
file adds about 20% to the in-memory time on Windows: for bf16 fast, 1.22 s against 1.02 s, which is
1.42 GB of stored bytes copied out of the cache at about 7 GB/s. On Linux from tmpfs it adds about 8%.
A raw random 1 MiB `seek_read` takes 0.17 ms against 0.08 ms with `pread`, the same 2x as memcpy.
`seek_read` therefore shows no slowdown beyond the cost of the slower machine and of the Windows cache.

**Multi-thread scaling is about the same.** Sequential decode with 12 threads gains 1.5x (through the
file) and 1.75x (in memory) over one thread on Windows, against 1.5 to 1.9x on the loaded Linux box. So
on both systems 12 threads gain little over one. That is a property of the read engine on both systems:
the calling thread reads a batch and then waits for it to be decoded. It is not a Windows problem.

**Anomaly: on Windows the decode pool makes small reads slower.** A 1 MiB random read touches two
1 MiB chunks. On Linux, decoding them on the pool cuts p50 from 0.49 to 0.31 ms. On Windows it raises
p50 from 1.16 ms (inline) to 1.27 to 1.37 ms with 2 to 12 threads, and p95 from 1.23 to about 1.85 ms.
Every pool dispatch costs a constant 0.1 to 0.2 ms, at any thread count from 2 up. This fits a slow
wake-up of rayon workers, or of parked cores under the Balanced power plan. That cause is a hypothesis:
it was not profiled, and the power plan was not changed. The effect is small next to a cold read from
disk (the v0.1 R2 gate is the raw p50 + 8 ms), and it does not touch sequential decode much: 170 batches
at about 0.15 ms each are about 25 ms of a 0.8 s read. Small reads served by `ReadCache`, as in the mount,
pay it once per window fill.

**Other observations.**

- Windows `restore` and `encode` include writing and syncing to NVMe, and Linux wrote to tmpfs, so
  their ratios (3.2 to 4.7) measure the storage, not the decoder. The Windows `restore` outliers at t=0
  took up to 2x the t=1 time, 6.86 s against 3.35 s for bf16 fast. They appeared only when writing a new
  file. They are consistent with an
  on-access scan or with cache flush timing, and were not investigated.
- `verify` adds a serial whole-member BLAKE3 to the decode: about 0.4 s for 2.1 GB on Windows and
  0.15 s on Linux. For F32, `verify` at t=0 was slightly slower than at t=1 on both systems (Windows
  0.78 to 0.80 against 0.71 to 0.77).

Not measured: cold-cache reads (Windows has no `posix_fadvise` equivalent in the probe), reads through
the WinFsp mount, and runs on battery.
